# Run the comparison for the user

For “Compare this capability against raw transcripts,” prepare and coordinate the comparison yourself. Never give the user a command-line checklist. State what was actually measured.

For a general outcome build, use its source run and build directory: `python SKILL_ROOT/scripts/evaluate.py pair --run RUN --package BUILD --output NEW_EVALUATION_DIR --tasks TASKS --rubric RUBRIC`. The brief is included automatically and no skill export is needed. For legacy builds, --package takes the packaged method directory and --context BUILD/brief.json supplies context. Ensure RUN's current IR matches the build; for older builds use an isolated copy with the build's historical IR, never overwrite active knowledge. The command freezes shared context and creates effort.json with unmeasured values. Legacy compare remains supported for standalone skills.

Both arms get the same full sources and goal/constraints. Both may save notes and methods in separate persistent workspaces; the baseline may organize material as well as ordinary chat permits. Start isolated, but preserve each arm's own context for subsequent tasks. Follow with a different goal and then an identical source update. Record initial setup, reuse and update active user minutes, assistant time, messages, corrections and human quality ratings in effort.json. Include compilation time in initial cost. Do not reset baseline memory between stages. See [the protocol](../docs/EVALUATION.md).

1. Call the coordinator with `--intent compare` and a selection if needed. At `prepare_evaluation`, save held-out tasks/rubric at the returned paths. Prefer supplied independent cases; otherwise create clearly labeled assistant-authored new examples. `fixtures/held-out/` illustrates gardening; `fixtures/flows/` has photography and debugging suites. Use fixtures only with their matching source domain.
2. Tasks form an array with `case_id`, `task`, `decision_fields` mapping names to allowed string values, and optional boolean `requires_citations` (default true; unsupported requests may set false). A rubric has `expected_decisions` by case ID with those fields, `human_dimensions` mapping names to rating explanations, and optional `notes`. Keep expected answers out of tasks. Exercise missing information, transfer, scope limits, and relevant disagreements. A chosen operating policy is not scientific ground truth.
3. Rerun compare, optionally with `--tasks PATH --rubric PATH`. It creates self-contained `baseline-prompt.md`, `compiled-prompt.md`, response template, and frozen task/rubric snapshots bound to the IR and selected capability. Both arms get identical tasks. Expected answers remain separate. Preparation is not a measured win.
4. Use authorized fresh isolated sessions if available, with the same model/settings and no compilation/rubric context in either. Otherwise give the user the two ready-to-paste prompts for separate fresh chats and ask them to return the answers. This is a context-isolation limitation, not a request to operate the compiler. Do not answer twice in this informed context and claim independence. Do not launch model CLI processes or incur unapproved usage as a hidden workaround.
5. Save the returned answers and invoke the installed evaluator yourself: `score RESPONSE --arm baseline|compiled --run RUN --evaluation EVALUATION_DIR --output REPORT`. Explain decision matches/citation errors, then review prose entailment, scope, actionability, conflicts, and reuse. Prefer blind human review when feasible. Record model/date, setup/reuse time, repairs, and verification effort. Structured scores alone do not establish quality superiority.

Do not tune the skill using held-out answers and keep calling those cases held out. Changed tasks/rubrics need a new comparison. Keep all evaluation material outside exported skills.
